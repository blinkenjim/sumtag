- **`--digest` flag for selectable algorithms.** `xxh3` is the documented default (CLAUDE.md "Extended attribute schema"); `sumtag/hashing.py` already supports `md5` alongside it, selected today by hand-editing `schema.ALGO` (a temporary code-level switch, previously used for cross-checking against `md5sum`; `scripts/xxh3_crosscheck.py` now checks the real `xxh3` default directly via `xxhsum -H3`, so the switch is no longer needed for routine testing). A real `--digest` CLI flag should make the algorithm selectable at the command line, defaulting to `xxh3`, without requiring a source edit.

  Design resolved 2026-07-02 (see CLAUDE.md "Digest container", "Re-hashing logic", and Database storage's Schema section for the full writeup): the xattr's `digests` map holds exactly one entry, ever — never accumulates multiple algorithms simultaneously. Freshness is algorithm-agnostic (any current digest counts as up to date; switching the active algorithm never forces a re-hash by itself, which matters at TB scale). When a file does get re-hashed for any of the normal reasons, it computes under whichever algorithm is currently active and *replaces* the single stored digest. Deliberately re-stamping a whole archive under a new algorithm is `--force` (once `--digest` exists), same mechanism as today. Known consequence: dedup queries (`GROUP BY algo, digest`) won't find duplicates across files stamped under different algorithms — a documented hazard, left to higher-level dedup tooling to detect and warn about, not something sumtag itself needs to solve.

- **Moved/renamed-directory detection for the prune family (`--prune-moves`).** Designed 2026-08-05, not built. Today a moved or renamed directory is pruned at its old location like a deletion and re-added only when the new location is re-scanned — correct but wasteful of row identity (delete + re-add instead of update; locate columns and timestamps lost) even though the re-scan itself is already cheap (the xattr travels with the file and `rename(2)` preserves mtimes, so no re-checksumming ever happens; the cost is metadata-only). The design closes that gap **with no schema change**, using the file rows' recorded inodes rather than directory inodes (which the schema deliberately doesn't store — no directory table):

  1. *Lost set* — the vanished directories, exactly as `--prune-dirs` finds them, with their resident rows.
  2. *Found set* — gated on the lost set being nonempty: walk the roots with the shared walker and collect directories containing files but holding zero database rows (`os.scandir` supplies child inodes nearly free).
  3. *Match* — lost L matches found F iff **every** resident row of L has a child of F agreeing on all three of **(inode, basename, file_mtime to the stored microsecond)** — the dedupe trust-veto idiom, zero content I/O. Inode alone is never trusted (inode numbers recycle); the microsecond-mtime agreement makes reuse collisions essentially impossible. The subset direction (L ⊆ F) tolerates files added after the move; anything deleted/renamed/modified after the move breaks the match and falls back to prune-plus-rescan — the safe direction. Ambiguous claims (possible only via hard-link farms) are refused: warn, keep the rows, prune nothing there.
  4. *Act* — `UPDATE` the resident rows' `rel_path` prefix in place (resident-only, never recursive: a moved tree's subdirectories are independently lost, independently found, independently matched — the same composition that keeps `--prune-dirs` recursion-free). `mountpoint_id` never changes: a cross-filesystem move is copy+delete with new inodes, can never match, and correctly falls to prune+rescan. Announce `move <old> -> <new> (N file rows)` / `would move` under `-n`; summary gains `moved:`; verify-style exit codes; commits per matched directory; sink principle intact (no xattr touched, nothing ever hashed). Because it genuinely traverses, `--exclude`/`--no-ignore` are honored, not errors — unlike its siblings.

  **Flag topology — DECIDED 2026-08-05: no separate flag.** Move detection folds into `--prune-dirs` itself (and `--prune-all` inherits it by subsumption); the cost argument for a separate opt-in (a mass deletion paying a full-tree walk hunting moves that never happened) was heard and declined as not compelling. Two mitigations survive as *internal* behavior, not flags: (a) **tiered candidate search** — each lost directory's own *parent* is checked first (one `readdir` of a directory already being stat'd; renames-in-place, the likely-majority case, resolve here for nearly nothing), and only if unmatched lost directories remain does the tree-wide walk run; (b) **the walk is announced** when it happens (`N directories vanished; walking roots to check for moves` — the approximation-by-consent idiom), so a long run is never silent about why. Consequences to carry into CLAUDE.md and the man pages at implementation time: `--prune-dirs`/`--prune-all` stop being errors with `--exclude`/`--no-ignore` (the candidate walk genuinely traverses, and traversal-level exclusions apply wherever traversal happens); the "walks the database, not the filesystem" wording needs qualifying; `--progress` gains the walk phase. Still open (minor): whether an ambiguity-refusal is exit `2` (incomplete check — the lean) or a warning within exit `1`. Natural later increment, out of scope for the first cut: per-file rename detection inside surviving directories (same signature idea, row-by-row, on top of `--prune-all`).
