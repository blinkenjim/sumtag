- **`--digest` flag for selectable algorithms.** `xxh3` is the documented default (CLAUDE.md "Extended attribute schema"); `sumtag/hashing.py` already supports `md5` alongside it, selected today by hand-editing `schema.ALGO` (a temporary code-level switch, previously used for cross-checking against `md5sum`; `scripts/xxh3_crosscheck.py` now checks the real `xxh3` default directly via `xxhsum -H3`, so the switch is no longer needed for routine testing). A real `--digest` CLI flag should make the algorithm selectable at the command line, defaulting to `xxh3`, without requiring a source edit.

  Design resolved 2026-07-02 (see CLAUDE.md "Digest container", "Re-hashing logic", and Database storage's Schema section for the full writeup): the xattr's `digests` map holds exactly one entry, ever — never accumulates multiple algorithms simultaneously. Freshness is algorithm-agnostic (any current digest counts as up to date; switching the active algorithm never forces a re-hash by itself, which matters at TB scale). When a file does get re-hashed for any of the normal reasons, it computes under whichever algorithm is currently active and *replaces* the single stored digest. Deliberately re-stamping a whole archive under a new algorithm is `--force` (once `--digest` exists), same mechanism as today. Known consequence: dedup queries (`GROUP BY algo, digest`) won't find duplicates across files stamped under different algorithms — a documented hazard, left to higher-level dedup tooling to detect and warn about, not something sumtag itself needs to solve.

- **Require an explicit action flag; retire the bare default stamp mode.** Decided 2026-07-13. Every run must name its action — one of `--sum`, `--verify`, `--remove`, `--import`, `--locate` — and bare `sumtag /data` becomes a CLI error, extending the existing "no recursive operation by omission" rule (which already forbids a cwd default) from the directory to the verb. `--sum` becomes the name of the plain stamping action: it **no longer requires `--database`** — `sumtag --sum /data` stamps xattrs exactly as bare `sumtag /data` does today, and adding `--database` makes it also mirror. Its semantics are untouched: the mtime-based re-hash decision still governs, so `--sum` over an up-to-date tree computes nothing. That skip behavior is load-bearing, not a bug — cheap re-runs and resumed scans of TB-scale trees depend on it, and `--force` remains the compute-unconditionally override. `--prescan` (and the planned `--db-prescan`) are modifiers, never actions: with the unnamed default mode gone, `sumtag --prescan /data` fails the action requirement automatically, with no extra conflict rule. This is a **breaking CLI change** — CLAUDE.md usage/examples, the man page synopsis and examples, the conformance harness scenarios, and any user scripts using the bare form all change — and is the stepping stone to a future subcommand model (`sumtag sum /data`), where an action subcommand is structurally mandatory. The verb's name can be revisited at that migration (`sum` reads like a promise to compute; `update` or `stamp` may be more honest about the converge-to-current semantics).

- **`--db-prescan`: filesystem-free prescan totals for huge trees.** Designed 2026-07-13, motivated by a 48TB filesystem whose `--prescan` alone took over an hour — and an interrupted `--sum` pays that hour again on restart. (Named to pair with `--prescan`; the earlier working name `--dbscan` was dropped for colliding with the DBSCAN clustering algorithm.) Two pieces:
  - **Persisting:** `--prescan` on a run that has `--database` (and is not `-n`) stores a single summary row in the database — file count, byte total, the scan roots, the full counting context (mode, whether `--force` was in effect, the `--exclude` patterns, and `--no-ignore` — everything that changes which files get counted), and a timestamp — replacing any previous row; one summary per database. The row persists until the next `--prescan --database` replaces it, so a resume-of-a-resume still has totals to load. This is deliberately *not* a per-file plan table: nothing ever reads the prescan data per file, so nothing more than the two totals plus matching context needs storing (a per-file table was considered and rejected — it would be a shadow inventory with lifecycle and two-sources-of-truth problems, feeding a cross-referencing behavior we explicitly don't want).
  - **Consuming:** `--db-prescan` is a `--prescan` alternative that reads mmm/bytes-total from the stored row instead of walking the filesystem (seconds instead of an hour). **Display-only by hard rule: it never influences the summing pass in any way** — the real pass walks the filesystem and makes every per-file mtime decision exactly as it does now; nothing is skipped or trusted based on stored data. `nnn` counts what actually happens, so it may overshoot the stored mmm (tree changed) or the run may finish below it (some work was already done — the "resumed" case): the user accepts an approximate progress report by choosing the flag. `--db-prescan` requires `--database`. The stored row is used **only if it matches the current run** — roots (strict set equality, compared after path normalization) and the full counting context; a missing row or any mismatch is a startup error (exit 2, before any work begins) telling the user to run `--prescan --database` first ("an error, not a silent no-op" — no silent fallback to the filesystem walk the flag exists to avoid, and no counterless multi-hour run). At startup `--db-prescan` announces what it loaded — `using stored prescan totals: 137 files, 4.2GiB, from <timestamp>` — on the normal output channel (suppressed by `-q`, byte figure honoring `--si`). Conflicts: with `--prescan` (two sources for the same counters) and with `--remove` (same reason as `--prescan`). `--verify` is excluded for v1: it conflicts with `--database` today, and its read-only invariant means it could never write its own mode-correct summary row; revisit only if verify's prescan cost warrants loosening that.
